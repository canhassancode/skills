# Delegating work artefacts between LLM agent contexts

## Scope

Asked: what sources establish as practice for moving work between LLM contexts — a fresh session, a subagent, a separate agent, or a human-reviewed stage — and what a handoff must carry. Four modes: (1) speccing, research and spiking; (2) exploration artefact to spec or ticket; (3) spec or ticket to implementation; (4) review of an idea's whole lifespan (intent and contract carried through to delivery).

Excluded: this repository's own skills and docs (deliberately not read), and any recommendation or design for the user's system. Findings only.

Evidence classes used throughout:

- **[measured]** — a number from a controlled study or a vendor-run evaluation (vendor-internal evals are flagged as such).
- **[first-party]** — practitioner guidance from the organisation that built the system, from its own experience, without a published measurement.
- **[opinion]** — argument, analysis or contested claim.

Dates are publication dates; "today" for this note is 2026-10-26.

## Cross-cutting findings

### Long or noisy context degrades the model — the underlying reason to start fresh

- Performance degrades as input length grows, even on trivial tasks (needle retrieval, text replication), across 18 models; on LongMemEval every model scored significantly higher on a ~300-token focused prompt than on the ~113k-token full prompt containing the same answer [measured] ([Chroma, Context Rot, 2025-07-14](https://www.trychroma.com/research/context-rot)).
- Relevant information is used best at the start or end of the context and worse in the middle [measured] ([Liu et al., Lost in the Middle, TACL 2023/24](https://arxiv.org/abs/2307.03172)).
- Across 15 LLMs and 200,000+ simulated conversations, underspecified multi-turn conversations scored on average 39% below fully specified single-turn prompts; the drop is mostly unreliability (+112%) rather than lost aptitude (−16%, non-significant). Models make early assumptions and "do not recover" [measured] ([Laban et al., LLMs Get Lost in Multi-Turn Conversation, 2025-05-09](https://arxiv.org/abs/2505.06120); numbers from the [HTML full text](https://arxiv.org/html/2505.06120)).
- The same paper's interventions: restating all prior requirements every turn ("snowball") recovers 15–20% of the loss but still trails a single fully specified prompt; the authors advise users to consolidate requirements and start a new conversation rather than continue a derailed one [measured + authors' guidance] ([Laban et al.](https://arxiv.org/html/2505.06120)).
- Anthropic names this "context rot" and frames context as a finite "attention budget" [first-party] ([Effective context engineering for AI agents, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Claude Code's docs: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills" [first-party] ([Claude Code best practices, current](https://code.claude.com/docs/en/best-practices)).
- Vendor-internal: context editing alone improved an agentic-search eval by 29%, context editing plus a file-based memory tool by 39%, and context editing cut token use 84% on a 100-turn web-search eval [measured, vendor-internal] ([Anthropic, Managing context, 2025-09-29](https://claude.com/blog/context-management)).

### When to fork the context vs keep it

- **Clear/restart triggers (first-party, Anthropic):** `/clear` between unrelated tasks; after two failed corrections on the same issue, clear and restart with a better prompt — "A clean session with a better prompt almost always outperforms a long session with accumulated corrections" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The same page also says sometimes you *should* let context accumulate when deep in one problem.
- **Keep work in the main thread** for frequent back-and-forth, iterative refinement, multi-phase work that shares a lot of context, quick targeted changes, or when latency matters; **use a subagent** for verbose output you don't need to keep, tool-restricted tasks, or self-contained work that returns a summary [first-party] ([Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)).
- **Maximise a single agent first;** split only when prompts accumulate complex conditional logic or tools overlap so much that clearer tool descriptions don't fix selection errors (some succeed with 15+ distinct tools, others fail with <10 overlapping ones) [first-party] ([OpenAI, A practical guide to building agents, 2025-04](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)).
- **Parallel reads vs parallel writes:** read actions parallelise more easily than writes; conflicting writes carry conflicting implicit decisions [opinion, synthesising Anthropic and Cognition] ([LangChain, How and when to build multi-agent systems, 2025-06-16](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)). Cognition's 2026 position: keep writes single-threaded; extra agents "contribute intelligence, not actions" [first-party] ([Cognition, Multi-Agents: What's Actually Working, 2026-04-22](https://cognition.com/blog/multi-agents-working)).
- **Task structure decides the sign of the effect.** Across 260 configurations on six agentic benchmarks, multi-agent coordination ranged from +80.8% on decomposable financial reasoning to −70.0% on sequential planning; returns diminish once the single-agent baseline is strong; tool-heavy tasks incur multi-agent overhead; architectures without centralised verification propagate errors more [measured] ([Kim et al., Towards a Science of Scaling Agent Systems, v1 2025-12-09, v3 2026-04-08](https://arxiv.org/abs/2512.08296); [Google Research blog, 2026-01-28](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). Earlier versions and secondary summaries quote 180 configurations and 17.2x vs 4.4x error amplification for independent vs centralised topologies; those figures are not in the v3 abstract.
- **Information-bottleneck framing:** with unbounded relay bandwidth a multi-agent system can simulate any single agent by passing the full upstream context; gains appear only when relays are near-sufficient (especially for weaker models) and shrink or reverse when relays lose task-relevant information (especially for stronger models) [measured, 18 controlled experiments, 5 benchmarks, 3 model scales; preprint] ([Yu et al., When Do Multi-Agent Systems Help?, 2026-07-17](https://arxiv.org/abs/2607.16133)).

### What a handoff must carry

- **Anthropic research system:** each subagent needs an objective, an output format, guidance on tools and sources, and clear task boundaries; vague instructions caused duplicated work (e.g. two subagents both researching 2025 supply chains) [first-party] ([How we built our multi-agent research system, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)).
- **Claude Code spec handoff:** the most useful specs "are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step" [first-party] ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Prompt guidance: reference specific files, mention constraints, point to example patterns, describe the symptom and what "fixed" looks like (same source).
- **A non-fork subagent starts with a clean slate:** it does not see the conversation or files already read, so the delegator must write a message that summarises the task, and the subagent may spend time re-gathering context [first-party] ([Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)).
- **Cognition's counter-requirement:** "Share context, and share full agent traces, not just individual messages," because "Actions carry implicit decisions, and conflicting decisions carry bad results" [opinion/first-party] ([Don't Build Multi-Agents, 2025-06-12](https://cognition.com/blog/dont-build-multi-agents)). In 2026 Cognition calls sharing a fork of the full context "a reasonable 80/20 solution" for model escalation [first-party] ([Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)).
- **Magentic-One task ledger:** given/verified facts, facts to look up, facts to derive, educated guesses, and a plan; a progress ledger asks each turn whether the request is satisfied, whether the team is looping, whether progress is being made, who acts next and with what instruction. Replacing the ledger-based orchestrator with a plain group-chat orchestrator cut GAIA validation performance 31% [measured] ([Fourney et al., Magentic-One, 2024-11-07](https://arxiv.org/html/2411.04468)).
- **Pointers, not payloads:** subagents write outputs to external storage and pass lightweight references back, avoiding loss across stages and token overhead [first-party] ([Anthropic research system](https://www.anthropic.com/engineering/multi-agent-research-system)); agents keep "lightweight identifiers (file paths, stored queries, web links)" and load just-in-time [first-party] ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)); Google ADK stores large data as versioned artefacts with only a name and summary in the prompt [first-party] ([Google Developers Blog, 2025-12-04](https://developers.googleblog.com/architecting-efficient-context-aware-multi-agent-framework-for-production/)).
- **Attribution on transfer:** ADK re-casts prior agents' assistant messages as narrative context and marks other agents' tool calls so the receiver does not mistake another agent's actions for its own; callee context can be scoped from full history (default) to none [first-party] ([Google ADK post](https://developers.googleblog.com/architecting-efficient-context-aware-multi-agent-framework-for-production/)). OpenAI's Agents SDK defaults the opposite way: the receiver "gets to see the entire previous conversation history," with `input_filter` and an opt-in beta that nests prior history into a summary block [first-party] ([OpenAI Agents SDK, Handoffs](https://openai.github.io/openai-agents-python/handoffs/)).
- **Return size:** subagents may burn tens of thousands of tokens but return "a condensed, distilled summary… (often 1,000–2,000 tokens)" [first-party] ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)); many detailed subagent reports still consume the parent's context [first-party] ([subagents docs](https://code.claude.com/docs/en/sub-agents)).
- **Human-engineering provenance (handoffs):** I-PASS (Illness severity, Patient summary, Action list, Situation awareness and contingency planning, Synthesis by receiver — the receiver restates and confirms) was introduced across nine hospitals; medical errors fell from 24.5 to 18.8 per 100 admissions (−23%) and preventable adverse events from 4.7 to 3.3 (−30%), with no change in handoff duration [measured, clinical] ([Starmer et al., NEJM 2014;371:1803–12](https://www.nejm.org/doi/full/10.1056/NEJMsa1405556); [AHRQ PSNet summary](https://psnet.ahrq.gov/issue/changes-medical-errors-after-implementation-handoff-program)). The intervention was a bundle (training, simulation, observation), not the mnemonic alone. No source found ties I-PASS to LLM agent handoffs directly.

### What gets lost, and how it is measured

- **MAST taxonomy** (1,600+ traces, 7 multi-agent frameworks, κ = 0.88) — 14 failure modes. Handoff-relevant prevalences: disobey task specification 11.8%, step repetition 15.7%, unaware of termination conditions 12.4%, reasoning–action mismatch 13.2%, task derailment 7.4%, fail to ask for clarification 6.8%, loss of conversation history 2.8%, conversation reset 2.2%, information withholding 0.85%, premature termination 6.2%, no/incomplete verification 8.2%, incorrect verification 9.1%. Category sums ≈ 44% system design, 32% inter-agent misalignment, 24% task verification [measured] ([Cemri et al., Why Do Multi-Agent LLM Systems Fail?, v1 2025-03-17, v3 2025-10-26](https://arxiv.org/html/2503.13657v3)).
- MAST interventions: better role specification +9.4% (ChatDev, GPT-4o); a high-level objective-verification step +15.6%; "not all failure modes are resolved" [measured] (same source).
- **Lossy compression:** Cognition fine-tuned smaller models specifically to compress action histories and calls it hard to get right [first-party] ([Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)). Compaction "doesn't give the agent a clean slate" [first-party] ([Anthropic, Harness design, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Claude Code lets users instruct compaction to preserve e.g. "the full list of modified files and any test commands" [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Implicit decisions:** the Flappy Bird example — one subagent builds a Super Mario-style background, another a mismatched bird — illustrates loss of unstated style decisions [opinion, illustrative, unmeasured] ([Cognition 2025](https://cognition.com/blog/dont-build-multi-agents)).
- No source found that measures information loss per handoff field (e.g. "dropping ruled-out options costs X%"). The information-bottleneck paper is the closest formal treatment.

### Token and cost trade-offs

- Agents use ~4x the tokens of chat; multi-agent systems ~15x. Token usage alone explained 80% of BrowseComp performance variance (95% with tool calls and model choice). Multi-agent (Opus 4 lead + Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on an internal research eval [measured, vendor-internal] ([Anthropic research system](https://www.anthropic.com/engineering/multi-agent-research-system)).
- Planner/generator/evaluator harness vs solo agent: 6 h / $200 vs 20 min / $9 (over 20x cost) for a markedly better app; a later Opus 4.6 run cost $124.70 over ~3 h 50 min [measured, single anecdotal runs] ([Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- Subagents count against the same usage limits and can be routed to cheaper models [first-party] ([subagents docs](https://code.claude.com/docs/en/sub-agents)).

## Mode 1 — Speccing, research, spiking

- **This is the mode where delegation is best supported.** Anthropic's multi-agent gains were on breadth-first research with independent directions [measured, vendor-internal] ([research system](https://www.anthropic.com/engineering/multi-agent-research-system)); Chase reads both Anthropic and Cognition as agreeing that parallel reading suits multi-agent [opinion] ([LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)); Cognition uses read-only subagents for codebase lookup [first-party] ([Cognition 2026](https://cognition.com/blog/multi-agents-working)).
- **Purpose of isolation is protecting the main context:** "use subagents to keep research out of it"; unscoped "investigate" requests read hundreds of files — fix by scoping narrowly or delegating [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)). Cognition describes Claude Code's subagents as answering well-defined questions and never working in parallel with the main agent [opinion] ([Cognition 2025](https://cognition.com/blog/dont-build-multi-agents)).
- **Separate exploration from implementation:** explore → plan → implement → commit, to avoid "solving the wrong problem"; skip the plan if the diff fits in one sentence [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Persist the plan outside the window:** the research lead saves its plan to memory because context beyond 200k tokens is truncated, and spawns fresh subagents with handoffs when limits approach [first-party] ([research system](https://www.anthropic.com/engineering/multi-agent-research-system)).
- **Synthesis stays single:** the research system parallelises reading but one agent writes the final report [first-party, as summarised] ([LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)).
- **Failure measured here:** duplicated searches and gaps from vague briefs [first-party, anecdotal] ([research system](https://www.anthropic.com/engineering/multi-agent-research-system)). No measured data found on how much "what has been ruled out" in a brief reduces duplication.

## Mode 2 — Exploration artefact → spec or ticket

- **Interview, write a spec, then start fresh:** have Claude interview the user, write SPEC.md, then "start a fresh session to execute it. The new session has clean context focused entirely on implementation" [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)). The measured analogue is Laban et al.'s "consolidate then restart" (the Concat condition approaches single-turn performance; sharded conversation does not) [measured] ([Laban et al.](https://arxiv.org/html/2505.06120)).
- **Spec content (first-party):** files and interfaces involved, out-of-scope, an end-to-end verification step ([best practices](https://code.claude.com/docs/en/best-practices)); user journeys and success criteria, excluding stack and design, which belong in a separate plan ([GitHub, Spec Kit, 2025-09-02](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)); requirements/acceptance criteria, design, and tasks as three files with review between phases ([Kiro specs docs, updated 2026-10-15](https://kiro.dev/docs/specs/)).
- **Spec granularity:** Anthropic's planner was told to stay at product context and high-level technical design, because wrong detailed specs "would cascade into the downstream implementation"; without the planner the generator under-scoped [first-party] ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- **Machine-checkable state over prose:** feature list as JSON with every feature initially failing and agents allowed to change only `passes`; the model is "less likely to inappropriately change" JSON than Markdown [first-party] ([Anthropic, Effective harnesses for long-running agents, 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Human checkpoint between phases:** Spec Kit says not to move on until the current phase is validated [first-party, no evidence offered] ([GitHub](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)). OpenAI: escalate to a human on exceeded failure thresholds and high-risk actions [first-party] ([OpenAI guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)).
- **Evidence for spec-driven tooling:** GitHub's and Kiro's pages give no metrics [first-party claims, unmeasured]. Böckeler's hands-on review found agents frequently not following all spec instructions, duplicated classes, repetitive multi-file specs, and Kiro turning a one-line bug into 4 user stories with 16 acceptance criteria; benefits were anecdotal and failures more concrete [opinion/practitioner report] ([Böckeler, martinfowler.com, 2025-10-15](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

## Mode 3 — Spec or ticket → implementation

- **Fresh session per implementation, carried by artefacts:** Anthropic's long-running harness hands off between context windows via a progress file, git history with descriptive commits, a JSON feature list, and an `init.sh`; each new session reads git log and progress, picks the highest-priority failing feature, and runs an end-to-end smoke test before new work [first-party] ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Failure modes it targets:** one-shotting too much and leaving a half-implemented, undocumented feature; a later session seeing progress and declaring the job done; leaving broken state; marking features complete without end-to-end testing [first-party] (same source).
- **Resets vs compaction is model-dependent:** with Sonnet 4.5, "context anxiety" made full resets with structured handoffs essential; Opus 4.5 largely removed it, so resets were dropped for automatic compaction [first-party] ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). This is an explicit case of older guidance being superseded by model change.
- **Sprint contracts:** generator and evaluator agreed what "done" meant and how to verify it before code was written (sprint 3 had 27 criteria); with Opus 4.6 sprints were removed and the evaluator moved to one end-of-run pass [first-party] (same source).
- **Verification inside the loop:** give the agent a check it can run (tests, build, screenshot diff); without one, "looks done" is the only signal [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)). Agents must gain "ground truth" from the environment at each step [first-party] ([Building effective agents, 2024-12-19](https://www.anthropic.com/research/building-effective-agents)).
- **Parallel implementation is the weak case:** most coding tasks have fewer truly parallelisable subtasks than research, and agents are "not yet good at real-time coordination" [first-party] ([research system](https://www.anthropic.com/engineering/multi-agent-research-system)); multi-agent variants degraded sequential planning by up to 70% [measured] ([Kim et al.](https://arxiv.org/abs/2512.08296)). Where fan-out is used, Claude Code isolates each subagent in its own worktree and recommends refining the prompt on 2–3 items before running the full set [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)); Cognition uses manager–child "map-reduce-and-manage" delegation [first-party] ([Cognition 2026](https://cognition.com/blog/multi-agents-working)).
- **Repo as system of record:** OpenAI's Feb 2026 "Harness engineering" post (Ryan Lopopolo, 2026-02-11) is reported to keep a short AGENTS.md pointing into `docs/` with checked-in execution plans and progress logs; the primary page returned 403 and these details come from secondary summaries only — **unverified** ([OpenAI, Harness engineering](https://openai.com/index/harness-engineering/)).

## Mode 4 — Review: intent and contract carried through to delivery

- **Self-evaluation is biased:** LLM evaluators recognise their own text above chance, and self-recognition correlates linearly with self-preference [measured] ([Panickssery, Bowman & Feng, NeurIPS 2024](https://arxiv.org/abs/2404.13076)). Across 20 LLMs, stronger capability is "often uncorrelated, or even negatively correlated" with low self-preference; a structured multi-dimensional rubric cut self-preference 31.5% on average [measured, preprint] ([Yang et al., 2026-04-24](https://arxiv.org/abs/2604.22891)).
- **Intrinsic self-correction does not reliably work:** without external feedback LLMs struggle to self-correct reasoning, and sometimes degrade; multi-agent debate gains are largely attributable to self-consistency [measured] ([Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)).
- **Separate the judge from the worker:** agents "reliably skew positive when grading their own work"; tuning a standalone evaluator to be sceptical is "far more tractable" than making a generator self-critical; the evaluator still talked itself into approving flawed work until its prompt was tuned against human judgement [first-party] ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The evaluator was unnecessary for tasks within the generator's solo capability and still useful at its edge (same source).
- **Clean-context reviewer:** "A fresh context improves code review since Claude won't be biased toward code it just wrote" (Writer/Reviewer pattern); a subagent reviewer "sees only the diff and the criteria you give it, not the reasoning that produced the change"; to check against a plan, name the work, the plan, and what counts as a finding [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)). Cognition: Devin Review, with clean context, averages 2 bugs caught per Devin-written PR, ~58% severe; "clean context leads to a notable improvement in capabilities when using a generator-verifier loop" [first-party, vendor-reported numbers] ([Cognition 2026](https://cognition.com/blog/multi-agents-working)).
- **Reviewers over-report when asked to find gaps:** Anthropic warns a gap-hunting reviewer "will usually report some, even when the work is sound," leading to over-engineering; restrict findings to correctness and stated requirements [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)). Jin & Chen report LLMs often judge correct code non-compliant with its requirements, and that more detailed prompts (asking for explanations and fixes) raise misjudgement rates [measured, preprint, abstract gives no figures] ([Are LLMs Reliable Code Reviewers?, 2026-02-28](https://arxiv.org/abs/2603.00539)).
- **Verifiers are not a silver bullet:** MAST finds verification failures (premature termination, none/incomplete, incorrect) ≈ 24% of failures; "many existing verifiers perform only superficial checks"; adding a high-level objective check gave +15.6% [measured] ([Cemri et al.](https://arxiv.org/html/2503.13657v3)). Centralised verification reduces error propagation [measured] ([Kim et al.](https://arxiv.org/abs/2512.08296)).
- **Contract-protecting artefacts:** "It is unacceptable to remove or edit tests" in the feature list — guarding against an implementer weakening the contract [first-party] ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Show evidence (test output, commands, screenshots) rather than assert success [first-party] ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Traceability evidence:** mandatory per-line requirement citations (REQ IDs) enabled automated hallucination detection at 86–88% with 0% false positives on two models, while lowering output determinism (d ≈ −0.7); artefact-level (Spec Kit) or post-hoc trace maps detected 0% [measured, single-author preprint, N=20 and N=50 tasks] ([Panda, Citation Discipline in SDD, 2026-06-28](https://arxiv.org/abs/2606.30689)).
- **Human-engineering provenance:** IV&V is V&V performed with technical, managerial and financial independence from the developer (IEEE 1012, as described by [NASA IV&V](https://www.nasa.gov/ivv-overview) and [US DOL](https://www.dol.gov/sites/dolgov/files/ETA/advisories/UIPL/1998/UIPL38-98.html)); verification checks specified requirements are met, validation checks intended use. ISO/IEC/IEEE 29148 lists "traceable" among requirement quality characteristics ([secondary summary](https://publish.obsidian.md/petermilovcik/1+Notes/IEEE+29148); standard text not accessed). No source found that ties IV&V's three independence dimensions to LLM reviewers empirically; the agent sources address only *context* independence, not model-family independence.

## Persisted cross-session artefacts — worked examples

### Long-running coding harness (initialiser → coding agent)

- **Roles:** an initialiser agent runs once and expands the user's prompt into a comprehensive feature requirements file; a coding agent runs every later session in a fresh context. The two differ only in their initial prompt — system prompt, tools and harness are identical [first-party] ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Feature list (JSON):** entries carry `category`, `description`, `steps` (test steps) and `passes`; all start `false` ("over 200 features" for the claude.ai clone). Coding agents may change only `passes`: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." JSON was chosen because the model is less likely to inappropriately overwrite it than Markdown [first-party] (same source). The source's prose says "feature list" while its example transcript reads `tests.json`.
- **`claude-progress.txt`:** a log of what each agent has done [first-party] (same source).
- **Git:** an initial commit of the scaffold, then a commit per change with descriptive messages so bad changes can be reverted [first-party] (same source).
- **`init.sh`:** starts the development server and supports a basic end-to-end check [first-party] (same source).
- **Session startup:** `pwd`; read git log and progress file; read the feature list and pick the highest-priority failing feature; run `init.sh` and a basic end-to-end test to catch broken or undocumented state before new work [first-party] (same source).
- **Failures the artefacts target:** one-shotting and running out of context mid-feature, leaving work half-done and undocumented; later agents declaring the project finished early; features marked complete without end-to-end testing until browser automation was required [first-party, observed, unquantified] (same source).
- **Stated limits:** no quantitative results on whether later sessions kept to the spec; unclear whether a single general agent beats a multi-agent setup; optimised for full-stack web apps [first-party] (same source).

### Planner → generator → evaluator harness

- **Planner:** expands a 1–4 sentence prompt into a product spec (features, user stories, data model, visual design language), deliberately high-level so wrong technical detail does not cascade [first-party] ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- **Sprint contract:** before each sprint the generator proposed what it would build and how success would be verified; the evaluator reviewed it until both agreed (sprint 3: 27 criteria). Removed in the later Opus 4.6 harness in favour of one end-of-build evaluation [first-party] (same source).
- **File-based communication:** one agent writes a file; the other replies in the same file or a new one [first-party] (same source).
- **Reset handoff:** with Sonnet 4.5, context resets started a fresh agent with a structured handoff carrying "the previous agent's state and the next steps"; dropped for automatic compaction from Opus 4.5 [first-party] (same source).

### Research system (single writer, parallel readers)

- 3–5 subagents run in parallel with their own context windows and return condensed results (e.g. a list of companies); the post gives no return size [first-party] ([Research system](https://www.anthropic.com/engineering/multi-agent-research-system)). The 1,000–2,000-token figure comes from [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), not this post.
- Larger outputs: subagents "call tools to store their work in external systems" and pass lightweight references back; the post says this suits code, reports and data visualisations [first-party] (same source).
- The lead agent alone writes the final answer; a separate CitationAgent then places citations [first-party] (same source). The post does not discuss read vs write parallelism explicitly; that framing is LangChain's and Cognition's.

### Reader/writer in coding

- Neither Anthropic coding harness uses parallel readers feeding one writer. Both are sequential relays — one agent writes at a time and persisted files carry the work forward [first-party] ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). "Most coding tasks involve fewer truly parallelizable tasks than research" [first-party] ([Research system](https://www.anthropic.com/engineering/multi-agent-research-system)).

### When context becomes an artefact

- No source gives a token threshold (100k or otherwise) for moving context into a persisted artefact.
- Closest: the research lead saves its plan to memory because context beyond 200,000 tokens is truncated; near the limit agents summarise finished phases, store essentials externally, and spawn fresh subagents with handoffs [first-party] ([Research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Claude Code's docs state degradation "as it fills" without a number ([best practices](https://code.claude.com/docs/en/best-practices)). The reset trigger was model-dependent (Sonnet 4.5 vs Opus 4.5) ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

### Did implementation follow through on the spec?

- **Partly, unmeasured.** The first planner harness's spec ran to 16 features across ten sprints and the generator built most of it; without the planner the generator under-scoped [first-party, single runs] ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- **Drift observed:** in the DAW run, QA found clips could not be dragged, instrument and effects panels missing or display-only, and recording stub-only, noting "the spec explicitly calls for them"; the generator "was still liable to miss details or stub features when left to its own devices" [first-party] (same source).
- **The drift was caught by the independent evaluator, not prevented by the generator;** the evaluator itself needed several tuning rounds and still missed deeper bugs [first-party] (same source).
- Consistent with: agents not following all spec instructions ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)) and "disobey task specification" at 11.8% of multi-agent failures [measured] ([Cemri et al.](https://arxiv.org/html/2503.13657v3)).

## Where sources disagree

| Question | Position A | Position B | Scope / reconciliation |
|---|---|---|---|
| Multi-agent or single thread? | Anthropic: multi-agent +90.2% on research, worth ~15x tokens ([2025-06](https://www.anthropic.com/engineering/multi-agent-research-system)) | Cognition: single-threaded linear agent; multi-agent collaboration "only results in fragile systems" in 2025 ([2025-06](https://cognition.com/blog/dont-build-multi-agents)) | A is read-heavy research; B is code writing. Chase reconciles on reads vs writes ([LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)). | What crosses the boundary? | Full trace / context fork (Cognition; OpenAI SDK default full history) | Clean slate with a written brief and condensed return (Claude Code non-fork subagents; ADK `include_contents=none`; Anthropic research system) | Bottleneck paper: full context dominates if bandwidth is unbounded; compression helps only when near-sufficient ([Yu et al.](https://arxiv.org/abs/2607.16133)). Reviewers are the case where all sources prefer clean context. |
| Reset or compact? | Resets essential (Sonnet 4.5, context anxiety) | Compaction sufficient (Opus 4.5+) | Same author, model-dependent ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). |
| Detailed or high-level specs? | Spec Kit / Kiro: detailed multi-file specs with acceptance criteria | Anthropic planner: high-level, because wrong detail cascades; Böckeler: verbose specs are a review burden and agents ignore parts | No controlled comparison found. |
| Is an independent evaluator needed? | Yes for subjective work and at the capability edge | Unnecessary overhead for tasks within solo capability (Opus 4.6) | "The evaluator is not a fixed yes-or-no decision" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). |

## Evidence strength and gaps

- **Strongest measured evidence:** long-context degradation (Chroma; Lost in the Middle), multi-turn underspecification loss and consolidate-then-restart (Laban et al.), self-preference bias (Panickssery et al.), failure of intrinsic self-correction (Huang et al.), MAST failure prevalence, task-structure dependence of multi-agent benefit (Kim et al.), and I-PASS for human handoffs.
- **Vendor-internal measurements, not independently reproduced:** Anthropic's 90.2%, 15x, 80% variance, 29/39/84% context-management numbers; Cognition's 2 bugs/PR and 58% severe; Anthropic harness costs (single runs).
- **Asserted but unmeasured:** that a fresh session after spec-writing beats continuing (supported only by analogy to Laban et al.); the specific content list for a spec (files, interfaces, out-of-scope, verification step); that recording "what has been ruled out" prevents duplicated work; that spec-driven tooling (Spec Kit, Kiro) improves outcomes — no metrics published by GitHub or AWS; that human phase gates improve outcomes for agent pipelines.
- **No study found** that measures intent drift end-to-end from exploration through spec to merged code, or that compares same-model vs different-model reviewers on code-review recall. The traceability preprint (Panda 2026) is small and single-author.
- **No token threshold** is published for converting context into a persisted artefact; the only number is the research system's 200k truncation limit.
- **No follow-through rate** is published for implementation agents executing a spec persisted by an earlier agent; Anthropic's harness posts report single runs and observed drift only.
- **Fast-moving:** guidance has already been revised by model releases (resets → compaction; sprint contracts → single end pass; Cognition's 2025 → 2026 position). Anthropic: "Every component in a harness encodes an assumption about what the model can't do on its own" and these go stale ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- **Not accessed:** OpenAI "Harness engineering" (403), NEJM full text (403 — figures from AHRQ and secondary summaries consistent with the abstract), ISO 29148 and IEEE 1012 normative text.
