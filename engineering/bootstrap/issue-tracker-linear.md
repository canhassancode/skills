# Issue tracker: Linear

Issues for this repo live in **Linear**; a spec is its ticket's description. All operations go through the **Linear MCP** (`linear-server` tools) — there is no CLI.

Linear is almost always a **shared team workspace**. The governing principle is **adopt-don't-impose**: map onto the taxonomy the team already has, and **never create labels, workflow states, or Projects that don't already exist**. On first use, call `list_teams`, `list_issue_statuses`, and `list_issue_labels` to read the current taxonomy before writing. This file carries both lanes' conventions.

## Roles

Roles ride as **labels**, alongside the team's native delivery states; won't-fix is the exception — a native state. Record the mapping you settle on in the repo's `docs/agents/triage-labels.md`, which wins over these names.

| role | Linear target | notes |
| --- | --- | --- |
| `needs-triage` | the team's own triage label (`To triage`) | adopt the team's; a ported `needs-triage` is a duplicate to retire |
| `needs-info` | `needs-info` | no team equivalent — keep |
| `needs-alignment`, `ready-to-propose`, `awaiting-decision`, `ready-to-cut`, `ready-to-build` | the same names | the personal planning lane — never impose it on the team's taxonomy |
| `wontfix` | native `Canceled` | close by state, no label |
| `bug` / `enhancement` | `Bug` / `Feature` (or `Improvement`) | adopt the team's; ported lowercase labels are duplicates to retire |

## Disclaimer

The AI disclaimer defaults to **ON** on Linear (a shared team space, where AI authorship signal has value for teammates). Every triage comment and issue body opens with `> *This was generated by AI during triage.*` unless the repo sets `triage-disclaimer: off`.

## What does not apply on Linear

- **No label bootstrap.** Detect and map; never create taxonomy in a workspace you don't own without explicit maintainer sign-off.
- **AFK caveat.** The takeable state is only grabbable if the Linear MCP is authenticated in the headless runtime. The natural split: the agent reads the ticket from Linear (MCP) and ships code via a GitHub PR (`gh`); a human closes the Linear issue.

## Conventions

- **Agent-grabbable state**: apply the `ready-to-build` label — the planning lane's takeable state.
- **Read an issue**: `get_issue` for the body, `list_comments` for the discussion.
- **Write a spec**: `save_issue` with `description` set to the whole spec, replacing what was there.
- **Reference** issues by their `CAR-###` identifier (or URL), not `#N`.
- Won't-do → native `Canceled` state.
- Duplicate → `save_issue` with `duplicateOf: <survivor>`, the native duplicate relation, then `save_comment` naming the survivor's `CAR-###`.

## Publishing a cut

`/cut` publishes a parent spec's children. The semantics live in the skill; these are the operations.

- **Each child** — a sub-issue of the parent, in build order: `save_issue` with the parent set and the `needs-alignment` label.
- **Blocking edges** — Linear's native **blocking relation** is the live gate, set as each child lands; the body's `Blocked by` line repeats the identifiers for a cold reader.
- **The parent** — drops `ready-to-cut` once every child exists: `save_issue` with the label removed. Its spec's Children list becomes a checklist naming each child's `CAR-###`; it stays open until the last child merges.

## Pull requests as a triage surface

N/A. Linear has no PR concept, and the planning lane doesn't triage — its work is cut from an agreed parent spec, not classified.

## When a skill says "publish to the issue tracker"

`save_issue`.

## When a skill says "fetch the relevant ticket"

`get_issue` for the body, `list_comments` for the discussion.

Confirm the exact MCP calls — especially setting blocking relations — against the live server before relying on them; run `list_teams` / `list_issue_statuses` / `list_issue_labels` first, per adopt-don't-impose.
